**Status:** Done (etapas 1 a 3 em produção; etapa 4 descartada)
**Produção:** Worker `f1363d6f` (24/09/2026) · release [`v1.2.0`](https://github.com/filipecalegario/strateegia-mcp/releases/tag/v1.2.0) com o `.mcpb`
**Prioridade:** Alta
**Relatório de referência:** diagnóstico publicado como artifact em 23/09/2026 ("Strateegia MCP 2026")

## Contexto

A especificação corrente do Model Context Protocol é a **2026-07-28**, publicada em 28/07/2026. É a maior revisão desde o lançamento: o protocolo ficou sem estado. Não há mais o handshake `initialize` / `notifications/initialized`, o cabeçalho `Mcp-Session-Id` foi removido, e cada requisição carrega versão, capacidades e identidade do cliente no `_meta`. O servidor passa a ser obrigado a responder `server/discover`.

Na mesma época a Cloudflare declarou o `McpAgent` depreciado e congelado (`agents` 0.20), recomendando `createMcpHandler` com o SDK v2 (`@modelcontextprotocol/server`), que não usa Durable Object.

Até esta spec, o servidor usava `agents` 0.9 e `@modelcontextprotocol/sdk` 1.29, que negocia no máximo a versão `2025-11-25`, com um Durable Object por sessão.

#### Etapa 2 · o que foi implementado

- **Anotações em todas as 20 tools**, a partir de um vocabulário compartilhado em `src/tools/annotations.ts`. Os quatro campos são sempre declarados: quando omitidos, os padrões do MCP são os mais cautelosos (`destructiveHint: true`, `openWorldHint: true`), e o Claude tratava até as tools de leitura como potencialmente destrutivas. `openWorldHint` é `false` em todas, porque elas falam com um sistema fechado (a API do Strateegia) e não com a web aberta.

| Classe | Hints | Tools |
|---|---|---|
| `READ_ONLY` | só leitura | `list_projects`, `get_project`, `list_maps_in_project`, `get_map`, `get_point`, `list_tool_templates` |
| `ADDITIVE` | cria algo novo; repetir cria de novo | `create_project`, `create_map`, os 4 `create_*_point`, `add_monitor_status`, `add_question_to_divergence_point`, `add_comment_to_question`, `reply_to_comment` |
| `REVERSIBLE_SET` | define um estado fácil de desfazer; idempotente | `update_point_position`, `like_comment`, `unlike_comment` |
| `OVERWRITE` | substitui conteúdo existente; destrutiva | `update_divergence_point` |

- **Desvio do plano:** o plano dizia "nenhuma destrutiva". Na implementação, `update_divergence_point` ficou com `destructiveHint: true`, porque ela substitui título e introdução, e o texto anterior (a introdução pode ter até 20 mil caracteres) não é guardado. Nenhuma tool apaga entidades, então a decisão de não expor deleção continua valendo.
- **`isError: true`** em toda falha: `apiErrorToMcpResult` e um novo helper `toolError`, usado nas 4 falhas internas de `points.ts` (tipo errado, ponto não encontrado, falta de `questions`/`tool_id` e update sem campos).
- **JSON compacto** nas 21 respostas: `get_map` resumido passou de 43.728 para 28.964 bytes (34% menor), e `get_point` de um monitor, de 4.607 para 3.556 bytes (23% menor).

#### Etapa 3 · o que foi implementado

**Respostas de autenticação.** Antes de mudar, medi o comportamento do `mcp-remote` 0.14.3 com key vazia e com key inválida: em qualquer 401, ele inicia o OAuth, tenta Dynamic Client Registration em `/register`, recebe 404 e encerra com `Dynamic Client Registration rejected (HTTP 404): Not found`. A mensagem "Invalid API key" do servidor nunca chegava ao usuário. Testei três variantes num servidor local:

| Variante | Comportamento do `mcp-remote` 0.14.3 |
|---|---|
| A: 401 + `WWW-Authenticate` (o plano original) | ignora o cabeçalho, entra no OAuth e falha com "Not found" |
| B: 403 | não tenta OAuth e mostra a nossa mensagem como está |
| C: 401 + rotas OAuth com erro em JSON | entra no OAuth e mostra a nossa mensagem embrulhada em "Dynamic Client Registration rejected" |

A implementação combina B e C, separando os casos:

| Situação | Resposta |
|---|---|
| Sem cabeçalho `Authorization` | 401 com `WWW-Authenticate: Bearer` (credencial ausente) |
| Cabeçalho presente, key vazia ou rejeitada pelo Strateegia | 403 com instrução de como corrigir |
| `/.well-known/*`, `/register`, `/authorize`, `/token` | 404 com erro OAuth em JSON: "This MCP server does not use OAuth. Configure the header…" |

O 403 para credencial rejeitada foge do uso clássico (RFC 6750 sugere 401 para token inválido), mas a autorização OAuth do MCP é opcional e este servidor não a implementa. Na prática, o 401 empurra os clientes para um fluxo OAuth que não existe aqui.

**Bundle `.mcpb`:** `mcp-remote` fixado em 0.14.3 (antes `^0.1.38`, que prende o npm na série 0.1.x), manifest 1.2.0, CLI `@anthropic-ai/mcpb` fixada em 2.1.2 no script `mcpb:pack`. O ponto de entrada (`dist/proxy.js`) é o mesmo e o manifest passa no `mcpb validate`.

**Cache:** `tools/list` e `server/discover` saem com `ttlMs: 300000` e `cacheScope: "public"`. A lista é igual para todos e não tem dado pessoal; 5 minutos evita que uma tool nova fique invisível por muito tempo depois de um deploy.

**README:** reescrito com as 20 tools, a instalação por conector com Request headers (e a ressalva do beta), o `mcp-remote` fixado no exemplo manual, `"type": "http"` no exemplo do Claude Code e a tabela de respostas de autenticação.

## Etapa 1 · o que foi implementado

- `package.json`: `agents` 0.24.0, `@modelcontextprotocol/server` 2.0.0 e `@modelcontextprotocol/sdk` 1.30.0, fixados em versão exata porque o `agents` 0.24 declara esses peers com versão exata (a 2.1.0 do server é rejeitada pelo npm). `wrangler` 4.137.0.
- `src/index.ts`: o handler é criado uma única vez no módulo. A cada requisição, o Worker valida Authorization e Origin, troca a API key por JWT e chama `mcpHandler.fetch(request, { authInfo })`. A factory recebe `authInfo` e monta um `McpServer` novo com o JWT fechado na closure. Saem a classe `StrateegiaAgent`, o Durable Object e o cabeçalho interno `X-Strateegia-Jwt`.
- O `createMcpHandler` valida Origin por conta própria, com allowlist restrita a localhost e `workers.dev`. Como a validação de Origin já acontece no Worker (rejeita origens de rede privada), o handler usa `allowedOriginHostnames: "*"` para preservar o comportamento anterior.
- `src/tools/*.ts`: 20 registrações convertidas para `registerTool(nome, { description, inputSchema: z.object({...}) }, handler)`, sem mudar nomes, descrições, schemas nem handlers.
- `wrangler.jsonc`: migração `v2` com `deleted_classes: ["StrateegiaAgent"]`, binding removido, `compatibility_date` 2026-09-01.
- `worker-configuration.d.ts`: `Env` vazio, pois não há mais bindings.

## Riscos

- **Remover o Durable Object é irreversível** na configuração do Worker. Ele só guardava dados de sessão de transporte, então não há perda. O deploy desta etapa aplica a migração `v2`.
- **SDK v2 é recente.** As versões ficam fixadas; atualizações devem vir junto com a do `agents`, que dita os peers.
- **Clientes 2025 dependem do modo legado** (`legacy: "stateless"`, padrão). Se um dia ele for removido, o `mcp-remote` precisará falar 2026-07-28.
