# 007 · Conformidade com a spec MCP 2026-07-28

**Status:** In progress (etapa 1 em revisão)
**Prioridade:** Alta
**Relatório de referência:** diagnóstico publicado como artifact em 23/09/2026 ("Strateegia MCP 2026")

## Contexto

A especificação corrente do Model Context Protocol é a **2026-07-28**, publicada em 28/07/2026. É a maior revisão desde o lançamento: o protocolo ficou sem estado. Não há mais o handshake `initialize` / `notifications/initialized`, o cabeçalho `Mcp-Session-Id` foi removido, e cada requisição carrega versão, capacidades e identidade do cliente no `_meta`. O servidor passa a ser obrigado a responder `server/discover`.

Na mesma época a Cloudflare declarou o `McpAgent` depreciado e congelado (`agents` 0.20), recomendando `createMcpHandler` com o SDK v2 (`@modelcontextprotocol/server`), que não usa Durable Object.

Até esta spec, o servidor usava `agents` 0.9 e `@modelcontextprotocol/sdk` 1.29, que negocia no máximo a versão `2025-11-25`, com um Durable Object por sessão.

## Diagnóstico (17 itens)

| Item | Veredito |
|---|---|
| Versão de protocolo, handshake/sessão, `server/discover`, runtime `McpAgent`, registro via `server.tool()` | Migrar |
| Cabeçalhos `Mcp-Method`/`Mcp-Name`, cache `ttlMs`/`cacheScope`, fim do SSE legado | Resolvido pelo SDK v2 |
| Anotações de risco, `isError` nas falhas, `WWW-Authenticate` no 401, `mcp-remote` antigo no `.mcpb` | Ajustar |
| Saída estruturada (`outputSchema`) | Opcional |
| Autenticação por API key, validação de Origin, recursos depreciados não usados, ordem fixa da `tools/list` | Conforme |

## Plano em quatro etapas

A ordem é de dependência: cada etapa se apoia na anterior.

### Etapa 1 · Núcleo sem estado (obrigatória)

- Atualizar `agents` para 0.24 e adotar `@modelcontextprotocol/server` 2.x.
- Substituir `StrateegiaAgent` (McpAgent + Durable Object) por `createMcpHandler`.
- Remover o Durable Object com migração `deleted_classes` e atualizar a `compatibility_date`.

**Descoberta durante a implementação:** o `McpServer` do SDK v2 não tem mais `server.tool()`, só `registerTool`. Por isso a conversão mecânica das 20 registrações, prevista para a etapa 2, precisou entrar já na etapa 1. O restante da etapa 2 (anotações, `isError`, JSON compacto) segue separado.

### Etapa 2 · Tools no formato atual (obrigatória)

- ~~Migrar `server.tool(...)` para `registerTool`~~ (antecipado para a etapa 1).
- Declarar `annotations`: as 6 tools de leitura (`list_projects`, `get_project`, `list_maps_in_project`, `get_map`, `get_point`, `list_tool_templates`) com `readOnlyHint: true`; `update_*` com `idempotentHint: true`; nenhuma destrutiva.
- Fazer `apiErrorToMcpResult` devolver `isError: true`, para que falhas da API não cheguem ao modelo como resultado bem sucedido.
- Trocar `JSON.stringify(data, null, 2)` por JSON compacto (17 ocorrências).

### Etapa 3 · Acesso e distribuição (recomendada)

- Incluir `WWW-Authenticate: Bearer` nas respostas 401. Sem ele, o `mcp-remote` tenta descobrir OAuth, recebe 404 e encerra com erro fatal quando a key está vazia. O SDK v2 exporta `bearerAuthChallengeResponse`, que pode ajudar.
- Atualizar o `mcp-remote` do `.mcpb` (hoje `^0.1.38`, atual 0.14.3) e subir o manifest para 1.2.0.
- Documentar o conector remoto do Claude com **Request headers** (`Authorization: Bearer ‹api key›`), que dispensa o `.mcpb` onde o recurso beta estiver liberado.
- Ajustar `cacheHints`: hoje a `tools/list` sai com `ttlMs: 0` e `cacheScope: "private"` (padrões do SDK). Como a lista é igual para todos, pode ser `public` com TTL de alguns minutos.

### Etapa 4 · Oportunidades (opcional)

- MCP Apps (extensão `io.modelcontextprotocol/ui`) para o `get_analytics` da spec 002: painel de KPIs renderizado na conversa.
- Multi Round-Trip Requests para confirmar o envio de e-mails no `invite_to_project` da spec 003.
- `outputSchema` nas tools mais usadas.

## Etapa 1 · o que foi implementado

- `package.json`: `agents` 0.24.0, `@modelcontextprotocol/server` 2.0.0 e `@modelcontextprotocol/sdk` 1.30.0, fixados em versão exata porque o `agents` 0.24 declara esses peers com versão exata (a 2.1.0 do server é rejeitada pelo npm). `wrangler` 4.137.0.
- `src/index.ts`: o handler é criado uma única vez no módulo. A cada requisição, o Worker valida Authorization e Origin, troca a API key por JWT e chama `mcpHandler.fetch(request, { authInfo })`. A factory recebe `authInfo` e monta um `McpServer` novo com o JWT fechado na closure. Saem a classe `StrateegiaAgent`, o Durable Object e o cabeçalho interno `X-Strateegia-Jwt`.
- O `createMcpHandler` valida Origin por conta própria, com allowlist restrita a localhost e `workers.dev`. Como a validação de Origin já acontece no Worker (rejeita origens de rede privada), o handler usa `allowedOriginHostnames: "*"` para preservar o comportamento anterior.
- `src/tools/*.ts`: 20 registrações convertidas para `registerTool(nome, { description, inputSchema: z.object({...}) }, handler)`, sem mudar nomes, descrições, schemas nem handlers.
- `wrangler.jsonc`: migração `v2` com `deleted_classes: ["StrateegiaAgent"]`, binding removido, `compatibility_date` 2026-09-01.
- `worker-configuration.d.ts`: `Env` vazio, pois não há mais bindings.

## Riscos

- **Remover o Durable Object é irreversível** na configuração do Worker. Ele só guardava dados de sessão de transporte, então não há perda. O deploy desta etapa aplica a migração `v2`.
- **SDK v2 é recente.** As versões ficam fixadas; atualizações devem vir junto com a do `agents`, que dita os peers.
- **Clientes 2025 dependem do modo legado** (`legacy: "stateless"`, padrão). Se um dia ele for removido, o `mcp-remote` precisará falar 2026-07-28.
